## 零、我对你思路的理解（先对齐，避免做偏）

你这次的要求不是"再写一份调研"，而是给出一条**完整闭环**：

```
完整分析  →  改造方案  →  逐项改造(每项记录进度+补测试)  →  真实上游验证  →  汇总存疑
```

我提炼出你的 5 条核心约束，这些是贯穿全程的判据：

### 约束 1 · 额度是稀缺资源，测试要分层
账号大部分额度已耗尽。所以**不能想到什么就打上游**。
必须先产出测试策略文档，把用例明确分成三层：

| 层 | 手段 | 额度消耗 | 目标占比 |
|---|---|---|---|
| A | 纯单测（协议转换、字符清洗、解析） | 0 | 尽可能大 |
| B | mock 上游（故障转移、错误码、SSE 帧序） | 0 | 次之 |
| C | **真实 Kiro 上游** | 有 | 压到最小，且只放必须项 |

C 层只允许放「不打真实上游就根本无法判定」的问题（例如 `tokenUsage` 真值、
请求体上限、端点对 `Origin` 的实际要求）。

### 约束 2 · 测试通过 ≠ 问题解决（这是你反复强调的）
你明确说了：**"有些问题不一定是真实的问题或者是真实解决了，需要抱有怀疑态度"**。
因为测试环境有硬性局限：

- 只能测 **haiku / sonnet**（4.5 系列），**不能测 opus**
- 上下文只支持 **200k**
- 账号是 **KIRO FREE 个人号**，额度受限

→ 直接后果：**凡是依赖大上下文或 opus 才能触发的缺口，本轮根本无法证伪**。
典型如 G2（请求体积上限 ~615KB）——200k 上下文可能压根堆不出那个体积。
这类项必须在最终汇总里明确标成 **「未验证」**，绝不能因为"跑过了没报错"就写成已解决。

### 约束 3 · 导入本身就是一次真实测试
清空账号 + 导入 235 条，不只是准备数据，而是**对"添加账号弹层内 Kiro 导入"的真实检验**。
所以：报错条目**跳过而非中断**，并且要记录**跳过了哪些、为什么**——
跳过率和跳过原因本身就是测试结论。

### 约束 4 · 调度必须能绕开耗尽的账号
这是你点名的验证项：**"如果遇到账号调度报错，需要保证调度到的是额度正常的账号"**。
这不是"重试一下就行"，而是要验证：额度耗尽返回的错误码，
能不能正确触发故障转移 + 账号冷却，而不是直接把错误透传给用户。

> ⚠️ 这一条和 **G1（400 不在故障转移列表里）直接耦合**。
> 如果额度耗尽走的是 4xx 且不在 `shouldFailoverUpstreamError` 里，
> 调度就会卡死在坏账号上。**G1 因此从"生态调研发现"升级为"本次必须先修的前置项"**。

### 约束 5 · 界面测试用 Playwright 静默模式
如有必要才测界面，且 **headless**，不弹真实窗口。
